Abstract 
Businesses require natural -language access to databases without exposing records to large 
language models, as this compromises data confidentiality and conflicts with governance 
mandates. This research paper introduces QueryMind, a system that resolves this issue by 
transforming natural-language enquiries into secure SQL through a schema -aware retrieval-
augmented generation pipeline featuring SELECT -only validation. We tested the system on 
an e-commerce database with five different model configurations. The best setup, llama3.1-8b 
with mxbai-embed-large, achieved 100% accuracy across all benchmark queries. The entire 
pipeline averaged 33 seconds per query, with 86% of that time dedicated to LLM generation. 
The smaller models gave answers faster, in an average of 4 to 7 seconds, but they were only 
40 to 60 percent accurate. Security tests in five different situations indicated that the system 
could withstand SQL injection, XSS, and session- hijacking attacks. The performance of local 
and remote databases  was almost the same, with only a 7% difference in total processing 
times. The results show that bigger LLMs take longer to process, but they make SQL 
generation more accurate and safer. They also show that a fully local, schema -restricted setup 
is reliable and keeps data private.

Chapter 1 
Introduction 
This chapter introduces the topic of text -to-SQL systems supported by RAG and outlines the 
motivation behind developing a reliable, schema -aware approach. Section 1.1 presents the 
problem statement and the gaps observed in current text -to-SQL methods that form the basis 
of this project. Section 1.2 describes the objectives of the work, including the system’s scope 
and the constraints followed during development. Section 1.3 highlights the relevance of the 
project and the value it provides for improving accuracy, safety, and usability in database 
querying. 
1.1 Problem Statement 
Relational databases are widely used by organizations to store and maintain transactional, 
financial and customer  data. Making anything useful of that data usually involves writing 
longish SQL queries, skills which are generally possessed by database administrators or 
developers. This technical limitation alienates much of the decision -making audience, 
analysts and non-technical users who perform their own data exploration or analysis. 
So, the common issue is that it's not easy to convert natural -language questions to SQL. 
Manual clause generation is time- consuming, error-prone and unmanageable across business 
units. Plus, exposing (without any kind of restriction) whole databases to the user interfaces 
may cause quite a bit of trouble, if queries  are not properly validated or run within some 
limiting context. 
Text-to-SQL systems powered by large language models (LLMs) offer a promising solution. 
However, hallucinations; where the model fabricates table names or columns remain a serious 
risk. Retrieval -Augmented Generation (RAG) mitigates this by constraining the model's 
knowledge to verify schema components, making the query generation more accurate and 
secure.

The importance of this capability is growing. A report found that companies leveraging data -
driven decision-making are 23 times more likely to acquire customers, six times more likely 
to retain them, and 19 times more likely to be profitable [1]. Yet, another paper notes that 
only 20% of decision- makers have direct access to the data they need, citing technical 
complexity as a major blocker [2]. 
Organizations increasingly use relational databases to store and manage Our system fills this 
gap by allowing users to query data using arbitrary natural -language questions, all while 
enforcing schema awareness , validation, and read- only execution. This makes it especially 
valuable in spaces where security and auditable truth are paramount, like in finance, 
healthcare, and government. 
1.2 Project Objectives 
This project aims to develop a secure and schema- aware, query -based Text -to-SQL system 
which can be used by the  users to retrieve records from the database using natural language -
based questions. The  system leverages models such as Retrieval -Augmented Generation 
(RAG) and Large Language Models (LLMs) to efficiently convert natural language 
expressions made by a user into sound and validated SQL SELECT queries that respect data 
security. 
1.2.1 Scope 
The project will comprise the development of a prototype that receives natural -language 
input, retrieves relevant  schema context through semantic search, formulates an accurate 
LLM prompt, and executes a SQL SELECT query in possibly a sandbox. The prototype 
consists of a user interface, retrieval  engine, LLM Processing layer, and validator. It is 
designed to work with structured relational databases, specifically MySQL, and operates 
read-only using SELECT queries. Evaluation is performed with a controlled dataset and using 
predefined user questions, where we  measure the accuracy, latency and LLM robustness 
across various LLM and embedding combinations. 
1.2.2 Target Audience 
Analysts, auditors, business users, and technical personnel who need to get data without 
manually writing SQL are among the system's target users. Additionally, academic

1.2.3 Impact 
This project is designed out of students in the University of Bahrain, but these are universal

system for wider  deployment in other industries and regions. The focus is educational and 
exploratory with an eye to future extensions that could support industrial scale deployments 
or the integration in existing business intelligence systems. 
1.2.4 Limitations 
This version of the system does not support any form of data manipulation such as INSERT, 
UPDATE, or DELETE commands. It only accepts English- language questions and operates 
on one database schema at a time. It is also limited to MariaDB and MySQL relational 
databases and does not support other types of database or NoSQL data sources. 
1.2.5 Assumptions 
The system presumes that users access via legitimate database credentials and function within 
a secure and verified environment.  It expects the language model to only get schema context, 
not live data or sensitive values.  The design also assumes that ChromaDB, the vector store, is 
installed, set up, and isolated for each session so that schema embeddings stay linked to the 
right user. The backend further assumes that database permissions enforce read- only access, 
and that the host environment blocks unauthorized file s, networks, or model -level actions.   
These assumptions let the system focus on making SQL in a controlled way and running 
queries safely within certain limits. 
1.3 Contribution 
1. This project presents a schema- aware Retrieval -Augmented Generation method that 
confines the LLM to the authentic database schema, effectively mitigating 
hallucinations in all evaluated queries and allowing the optimal model configuration 
to achieve complete accuracy. 
2. We use a strict validation pipeline that makes sure SQL generation is safe and only 
allows reading. The system blocked all non- SELECT attempts, such as UPDATE, 
DELETE, and DROP, in five security tests, resulting in a 100 percent pass rate.

Chapter 2 
Literature Review 
This chapter reviews the foundations of natural -language access to databases and summarizes 
the most relevant systems and studies that influence the design of QueryMind. It has two main 
sections. Section 2.1 presents background concepts, including the evolution of Text -to-SQL, 
schema-aware approaches, and recent advances in LLMs and Retrieval -Augmented 
Generation (RAG). Section 2.2 presents related work, including commercial and academic 
systems. The chapter concludes with a summary of key findings in Section 2.3 and a 
discussion of how these findings relate to our project in Section 2.4. 
2.1 Background 
Early studies on natural language interfaces to databases concentrated on rule -based or 
template-based approaches that depended on fixed grammar and manually crafted patterns. 
These systems could handle simple questions, but they couldn't handle complex schemas or 
queries that involved more than one table. Neural sequence -to-sequence models made things 
more flexible by mapping natural language inputs directly into SQL statements, with the help 
of benchmark datasets like Spider. But these models had a hard time with domain shift, 
schema complexity, and making SQL that was unsafe or imagined. 
Recent advancements in large language models (LLMs) have improved natural -language 
understanding and structured output generation, enabling more accurate Text-to-SQL systems. 
Modern LLM deployment tools, such as Ollama, allow organizations to run models locally 
without relying on external APIs. This supports privacy- sensitive use cases where database 
records cannot be exposed to cloud services. Open- source LLMs, including Llama, Gemma, 
and Qwen  variants, provide controllable inference environments while maintaining 
competitive performance. 
Retrieval-Augmented Generation (RAG) has emerged as a key technique for improving 
accuracy and security in Text -to-SQL. Instead of giving the model full access to database 
content, RAG provides only schema metadata or the specific tables relevant to a user query. 
--- PAGE 14 ---
6 
 
This guided retrieval reduces hallucinations and constrains the model to valid table and 
column names. Industry sources highlight that restricting LLM access to metadata is essential 
for governance, privacy, and controlled SQL generation [3]. Academic work such as Zhai et 
al. shows that execution feedback and structured reasoning can further improve accuracy and 
reduce invalid queries [4]. 
Together, these developments establish the foundation for modern schema -aware, secure, and 
locally deployed Text-to-SQL systems like QueryMind. 
2.2 Related Work 
This section presents the systems and research -related work papers. It includes real -world 
tools, academic frameworks, and enterprise deployments relevant to the design of 
QueryMind. 
1. Exasol Governed Text-to-SQL System 
Exasol proposes an on -premises Text -to-SQL framework built on strict governance 
policies. The system enforces read-only SQL, restricts LLM visibility to metadata, and 
prevents access to raw records  [3]. It emphasizes operational control but lacks 
published accuracy or latency benchmarks. 
2. Zhai et al. (2025) Execution-Feedback Framework 
Zhai et al. introduce ExCoT -DPO, an execution- driven optimization method that 
improves Text-to-SQL accuracy using chain -of-thought reasoning and reinforcement 
signals based on execution correctness [4]. While experimentally strong, the work 
does not address governance, real-world deployment, or security concerns. 
3. LinkedIn Production Text-to-SQL System 
Chen et al. describe LinkedIn’s enterprise text -to-SQL platform powered by metadata 
graphs, query logs, and schema -aware retrieval [5]. The system enables large- scale 
internal analytics but achieves around 53 percent accuracy and provides limited 
transparency into its security and latency characteristics. 
4. text2sql.ai Commercial Platform 
text2sql.ai is a cloud- based Text -to-SQL service supporting more than twelve SQL 
engines, schema uploads, and an interactive interface [6]. Strengths include multi -
dialect support and ease of use. Limitations include subscription requirements, 
reliance on third-party infrastructure, and reduced privacy for sensitive workloads.

2.3 Summary 
The reviewed literature leads to several important observations: 
• LLM-based Text-to-SQL is increasingly viable, especially when paired with schema -
aware retrieval. 
• Privacy, governance, and auditability remain major concerns for organizations 
handling sensitive data. 
• Metadata quality strongly affects accuracy, especially for multi -table queries or large 
schemas. 
• Benchmarks show promising accuracy, yet real -world deployment is limited by token 
constraints, latency, and safety concerns. 
• Cloud-based tools deliver convenience but sacrifice control and confidentiality, 
motivating interest in local or open-source solutions. 
2.4 Relevance to Our Project 
Given prior findings in the literature, our  study addresses three knowledge gaps particularly 
well. First, in the Exasol system, read -only safe SQL generation is enforced by restricting the 
LLM to metadata and running every query inside secure process  [3]. Second, Zhai et al. 
(2025) point out how important  it is to assess and tune LLM output based on the execution 
feedback, justifying our choice of real databases as well for comparing different LLM and 
embedding model pairs  [4]. Third, the business model  proposed by Chen et al. (2025) in 
LinkedIn, also demonstrates that the performance and governance benefits of retrieval layers 
using schema metadata and historic frequency successful queries. We learn from these works  
extensive best practices (including metadata incorporation, prompt engineering, query 
verification and benchmarking) but extend them to a framework of more principled and 
reproducible evaluation where the focus is on data governance and real -world applicability  
[5]. The comparison with text2sql.ai shows how commercial tools rely on cloud infrastructure 
and broad database support to provide accuracy and convenience, although this comes with 
cost and reduced control. Our system offers a free and fully local alternative, suitable for 
privacy-sensitive environments, and provides a foundation for extending language support 
and safe write-operations in future versions [6].

Chapter 3 
Project Management 
This chapter explains the management approach used to plan, structure, and execute 
QueryMind. Section 3.1 describes the chosen Software Development Life Cycle (SDLC). 
Section 3.2 presents the risk management process applied throughout development. Section 
3.3 outlines the project activity plan, including task sequencing, timelines, and dependencies. 
Together, these sections show how the system was organized from initial requirements to 
implementation, testing, and evaluation. 
3.1 Process Model 
The Waterfall Software Development Life Cycle was chosen because this project went from 
requirements to evaluation in one full pass, without any iterative sprints. The Waterfall model 
is a linear and structured way of doing things. You must finish one phase before you can 
move on to the next. It is appropriate for scholarly and technical endeavors characterized by 
well-defined specifications and restricted iteration cycles [7]. Waterfall also works well in 
situations where the system's scope and limits are known ahead of time, like a controlled 
Text-to-SQL environment with fixed database schemas, set security rules, and set evaluation 
metrics. 
Waterfall supports predictable planning, clear documentation, and sequential verification 
steps, which are essential when dealing with components like schema extraction, SQL 
validation, and LLM pipeline integration. Since LLM behavior depends heavily on stable 
prompts, schema context, and validation rules, following a linear design–build–test structure 
reduces uncontrolled variability and supports reproducible results.

Figure 1. Phases of the Waterfall SDLC  shows the phases of the Waterfall SDLC. The

and analyzed performance, accuracy, and security outcomes.

each component met structural, functional, and security requirements before moving to the 
next phase.

vector search, and dynamic schema retrieval. The Waterfall model stresses finding risks early, 
fixing them before implementation, and stopping problems from spreading into later phases

validation needs to be safe.

4.2 System Requirements 
This section describes the expected behavior and features of the Text -to-SQL system. It 
includes both functional and non- functional requirements. Functional requirements define the 
core actions the system must perform. Non- functional requirements specify the qualities the 
system must meet during real use, such as security, speed, usability, and maintainability. 
4.2.1 Functional Requirements 
These requirements describe the core functions that enable the Text -to-SQL system to operate 
as intended. Each requirement can be validated by running the full pipeline and confirming 
the generated SQL, returned results, and system logs match the expected behavior. 
• Natural-Language Query Input 
o Type your questions in plain English into one box. Next, it shows the SQL that 
was made, the time it took to run, and the result rows.  Users don't need to 
know SQL. 
• Schema-Aware Query Generation (LLM + RAG)  
o Using Retrieval -Augmented Generation, the system only gets the database 
schema that is needed and sends it to the LLM. The LLM uses this context to 
make SQL that fits the structure of the database without ever seeing real data. 
• Read-Only SQL Enforcement 
o The system can only make SELECT statements in SQL. You can't run or 
create UPDATE, DELETE, INSERT, or DROP queries.  This keeps the data 
safe and follows the least privileged principle.

• Model Benchmarking and Comparative Evaluation 
o The system lets you test different combinations of LLM and embedding 
models against a set of questions that don't change. It automatically sends 
reports on SQL accuracy, result correctness, latency, and failure patterns to 
help with repeatable evaluation. 
• Dynamic Schema Visibility Based on User Role 
o Users who are logged in can only see the tables and columns they have 
permission to see. Schema retrieval, RAG context, and LLM behavior change

• Structured Error Handling 
o When queries fail validation, when schema context is missing, or when model

4.2.2 Non-Functional Requirements 
The non- functional requirements define the qualities the system must maintain across all 
features to ensure security, reliability, and usability. 
• Security is a primary focus. Database credentials operate under least -privilege access, 
and the SQL validator blocks any operation that is not a SELECT statement. The LLM 
never receives live records and only processes schema text, which prevents unintended 
data exposure. 
• Confidentiality is maintained through schema -only retrieval. The RAG module 
provides the model with metadata rather than actual table contents, and user 
permissions ensure that only authorized structures are visible. Error messages are 
intentionally generic to avoid leaking sensitive details. 
• Performance and scalability  are supported by schema chunking and vector storage, 
allowing the system to handle large schemas efficiently. Retrieval focuses on relevant 
tables only, reducing context size and improving response times. Model selection also 
enables quick demonstrations and controlled experiments. 
• Usability is strengthened by a simple interface with a single input box, a table viewer, 
example queries, and clear timing indicators. Results are displayed on  a clean, 
scrollable table that is easy to interpret.

• Maintainability is ensured through modular design. Each component : schema loader, 
retriever, LLM engine, validator, and executor  is independent, making updates and

The system architecture has a structured pipeline that changes natural -language questions into 
safe SQL queries through a series of tightly controlled steps. The user starts interacting with 
the system through the Flask web interface, where they log in  (connect to the database)  and 
ask a question. They can only see the tables that their role allows. From the start, this access 
control follows the least privilege rules. The schema loader obtains table names, columns, and 
relationships from the connected database when a question is sent. The vector index contains 
these metadata fragments, which the retriever uses to determine the schema elements that are 
most relevant to the user's question. This retrieval step makes sure that the LLM acquires a 
compact and accurate schema context that only has structural information and never actual 
records. This keeps things private while also helping the model create SQL that fits the 
schema. 
After the context is retrieved, the chosen schema segments and the user's question are sent to 
the LLM, which makes an SQL query that fits the structure of the database. Thereafter, the 
output goes to the validation layer, where strict safety rules are used to check the SQL. The 
validator checks to make sure that the statement is a SELECT query, that all the tables and 
columns it refers to exist, and that there are no harmful patterns like UPDATE, DELETE, 
INSERT, or DROP. Only queries that pass these checks are run. The executor runs the SQL 
with read-only credentials so that data can't be changed by mistake, and the results are sent 
back to the user in a clear table format. The system presents a clear and safe error message if 
something goes wrong at any point, such as invalid identifiers, unsafe SQL, or missing 
schema context. This design makes sure that the whole Text -to-SQL workflow is accurate, 
has a consistent schema, and runs safely.

5.2.3 How the System Uses Table Metadata in RAG, Validation, and Query 
Generation 
Table metadata is what makes the whole Text -to-SQL pipeline work. It tells the system how 
to organize the data. When someone asks a question, ChromaDB stores and indexes the 
schema definitions. The retrieval module then picks the tables that are most relevant to the 
query based on how similar they are in meaning. This gives the LLM a focused schema 
context.  This makes sure that the model only gets the metadata it needs to understand the 
structure of the database and not any other information that might be useful or misleading. 
To make sure that the SQL that was generated is safe and correct, the same metadata is used 
during validation. The validator makes sure that all the tables and columns that are referenced 
in the schema are there. It also enforces strict SELECT -only rules to stop people from doing 
things they shouldn't. The LLM creates SQL using a controlled schema context, and the 
validator enforces these rules.  This makes the final query more accurate, structurally sound, 
and in line with the real database.

5.4.1 Schema Extraction and Metadata Loading 
The schema extraction module connects to the MariaDB database and retrieves the complete 
structure of all accessible tables. This metadata is essential for providing context to the LLM 
during query generation. 
Pseudocode (app.py): 
FUNCTION load_schema_from_session(): 
    connection = connect_to_database(session_credentials) 
    IF connection is NULL: 
        RETURN NULL 
     
    tables = execute_query("SHOW TABLES") 
    schema_text = "" 
     
    FOR EACH table IN tables: 
        create_statement = execute_query("SHOW CREATE TABLE table") 
        schema_text += create_statement 
     
    close_connection() 
    RETURN schema_text, tables 
This function iterates through all tables in the connected database, retrieves their CREATE 
TABLE statements, and concatenates them into a comprehensive schema text that describes 
the database structure.
